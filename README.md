# backend-supabase

Backend del ecosistema Colportaje sobre Supabase: schema, migraciones, RLS, RPCs, Edge Functions y seed. Región **sa-east-1** ([ADR-012](https://github.com/Colportores/docs-organizacion/blob/main/docs/decisiones/ADR-012-backend-supabase-sa-east-1.md)).

**Estado: esquema inicial + infra de sync** — migración `0001` con todas las tablas V1 del cloud y RLS con políticas base; migración `0002` con el RPC de ingesta batch, el cache de `client_op_id` y el delta pull ([ADR-008](https://github.com/Colportores/docs-organizacion/blob/main/docs/decisiones/ADR-008-sync-engine-paquete-dart.md)); migración `0004` con el estado de la cuenta (`estado_cuenta()`, HU-AUTH-008); migración `0005` con la inscripción en campaña (`inscribir_colportor()`, HU-CAM-004); migración `0006` con la zona del colportor (`asignar_zona()`, HU-CAM-006); migración `0007` con las lecturas del panel; migración `0008` con el mapa de la campaña (ciudades, zonas RADIAL/ESQUINAS, PostGIS). Las políticas se refinan HU por HU desde Sprint 3.

## Contexto

Parte del sistema [Colportaje App](https://github.com/Colportores). El modelo de datos, la arquitectura y las decisiones viven en la [documentación de la organización](https://github.com/Colportores/docs-organizacion) — en particular [`esquema-datos.md`](https://github.com/Colportores/docs-organizacion/blob/main/docs/esquema-datos.md) y el [contrato de sync](https://github.com/Colportores/docs-organizacion/blob/main/docs/contrato-sync-engine.md) §2, que fija qué entidades viven acá.

- **La RLS es la autoridad de permisos** de todo el sistema. Los BFF reenvían el JWT del usuario; no deciden nada por su cuenta ([ADR-013](https://github.com/Colportores/docs-organizacion/blob/main/docs/decisiones/ADR-013-un-bff-por-aplicacion-en-workers.md)).
- La lógica de dominio que toca varias tablas vive en **RPCs de Postgres**, no en los BFF.
- Push FCM vía Edge Functions ([ADR-014](https://github.com/Colportores/docs-organizacion/blob/main/docs/decisiones/ADR-014-push-con-fcm-desde-edge-functions.md)).

## Reglas del esquema

- Todos los IDs son **UUID v7 generados en el cliente** — nunca `SERIAL` ni `AUTOINCREMENT`. `public.uuid_generate_v7()` existe solo para seeds y filas creadas del lado servidor.
- Toda tabla lleva `created_at`, `updated_at`, `created_by`, `deleted_at` (soft delete) y `sync_version`. `updated_at` y `sync_version` los pone el servidor por trigger; `authenticated` no tiene `DELETE`.
- Dinero en **centavos** (`integer`).
- Migraciones **forward-only**: una migración aplicada no se modifica nunca. Nombre `<timestamp>_<nnnn>_<descripcion>.sql`.
- `anon` no tiene privilegios: todo entra por el BFF con el JWT del usuario.
- **Un solo «hoy»: el de Montevideo.** La vigencia de una campaña (la lectura, la escritura, la inscripción y el estado de la cuenta) cuenta el día con `public.hoy_montevideo()`, nunca con `current_date`: la zona horaria de la sesión es UTC en Supabase y entre las 21:00 y las 24:00 de Uruguay ya es otro día (`0024`). Una función nueva que decida «hoy» la usa.

Los tests pgTAP (`supabase/tests/`) verifican estas reglas en cada PR: si una tabla nueva no cumple, CI falla.

**Todo el SQL del repo vive en `supabase/`**, y `scripts/check-sql-layout.sh` lo hace cumplir en CI. `supabase migration up` y `supabase db push` leen únicamente `supabase/migrations/`: un árbol de SQL en cualquier otro lado sale verde sin que nadie lo haya aplicado ni probado.

## Desarrollo

Todo corre en Docker; no hace falta el CLI de Supabase ni Postgres en el host.

```sh
docker compose -f compose.dev.yml build cli                               # una vez
docker compose -f compose.dev.yml run --rm cli bash scripts/db-migrate.sh # base vacía + migraciones
docker compose -f compose.dev.yml run --rm cli bash scripts/db-test.sh    # pgTAP
docker compose -f compose.dev.yml run --rm cli bash scripts/db-lint.sh    # plpgsql_check
docker compose -f compose.dev.yml run --rm cli bash scripts/db-reset.sh   # borrar y re-aplicar todo
docker compose -f compose.dev.yml run --rm cli bash scripts/db-seed.sh    # + datos de ejemplo (opcional)
docker compose -f compose.dev.yml run --rm cli psql "$DB_URL"             # consola
docker compose -f compose.dev.yml down -v                                 # apagar (la base no persiste)
```

- **Imagen y cachés compartidas.** `-p <nombre>` propio está bien para aislar contenedores y la base; la imagen (`backend-supabase-dev:latest`) es compartida por todos los proyectos.
  `docker compose build` solo cuando cambia `dockerfile.dev`.
- `db` es la imagen oficial `supabase/postgres` (mismos roles, schema `auth` y extensiones que producción), expuesta en el host en `localhost:55432` (`DB_PORT=` para cambiarlo).
- `cli` trae Supabase CLI, `psql` y `pg_prove`. El repo se monta en `/work`.
- Nueva migración: `docker compose -f compose.dev.yml run --rm cli supabase migration new <nnnn>_<descripcion>` y luego `db-migrate.sh`.
- `db-seed.sh` carga `supabase/seed.sql` (zonas, campañas, catálogo y precios de ejemplo, todos ficticios — issue #16). Es un paso aparte de `db-reset.sh`, a propósito: la suite pgTAP asume el catálogo vacío salvo sus propios fixtures (p. ej. `0002_rls_test.sql` cuenta exactamente 1 fila en `producto`), así que sembrar datos de ejemplo no es parte del reset que usa CI. `db-seed.sh` es el **único camino sancionado**: `[db.seed] enabled = false` en `config.toml` a propósito, para que `supabase db reset --linked` (el comando nativo del CLI contra un proyecto remoto linkeado) **no** aplique el catálogo ficticio sobre staging/producción. Para cargar datos **reales** en vez de los de ejemplo, ver [`docs/guia-carga-manual.md`](./docs/guia-carga-manual.md).

## CI/CD

- `ci.yml` (PR y push a `develop`/`staging`/`production`): levanta el mismo `compose.dev.yml`, aplica todas las migraciones sobre una base vacía, corre pgTAP y `supabase db lint`, y al final prueba las migraciones que mueven datos con `db-test-migracion.sh`. Antes de levantar nada corre dos controles sin Docker: `check-sql-layout.sh` (todo el SQL vive en `supabase/`) y `check-config.sh` (`minimum_password_length` del `config.toml` no baja del de la app).
- `tiles.yml` (a mano, `workflow_dispatch`, y cada hora para los mapas de las zonas, solo en los environments con su variable `MAPAS_ZONAS_<ENV>` en `true`): publica los mapas propios (PMTiles de OpenStreetMap, estilo y catálogo; las ciudades salen de `public.ciudad`) en el bucket público `mapas` del environment y lo verifica. No lleva secretos nuevos. [`docs/mapas-tiles.md`](./docs/mapas-tiles.md). El job **tiles** de `ci.yml` corre las pruebas del publicador (`npm ci && npm test` en `tiles/`).
- `deploy.yml`: `supabase link` + `supabase db push` contra el proyecto Supabase del *environment*. **Se dispara al terminar CI en verde sobre el mismo commit**, nunca en paralelo: una migración que rompe pgTAP no llega a la base real.

### Cuándo aplica cada rama

| rama | aplica | condición |
|---|---|---|
| `develop` | environment `develop` | solo si la variable de repo **`DEPLOY_DEVELOP`** vale `true` |
| `staging` | environment `staging` | siempre, con CI verde |
| `production` | environment `production` | siempre, con CI verde |

El auto-deploy de `develop` va detrás de una bandera y no de un cambio de workflow: durante la fase de desarrollo conviene que cada merge deje el proyecto cloud al día, y eso deja de ser aceptable en cuanto arranque el piloto. Apagarlo es cambiar una variable:

```sh
gh variable set DEPLOY_DEVELOP --repo Colportores/backend-supabase --body false
```

También se puede disparar a mano contra cualquier environment desde la pestaña Actions (`workflow_dispatch`), o con `gh workflow run deploy.yml -f environment=develop`.

**`supabase/config.toml` no viaja con `db push`.** Vale para el Supabase local y para CI; el proyecto hosteado se configura aparte, con `supabase config push` o desde el panel. Pendiente de despliegue en cada environment (backend-supabase#59): `minimum_password_length = 8` (Authentication, política de contraseñas), el mismo mínimo que la app, para que el servidor no acepte una contraseña que la app rechaza. `password_requirements` queda vacío a propósito: la mayúscula (cualquier letra mayúscula Unicode, con tilde o Ñ) la valida la app.


## Infraestructura de sincronización

Lo que ADR-008 pone de este lado: RPC de ingesta batch, cache de `client_op_id` (TTL 24 h) y delta pull. Vive en el schema `sync`, que **no se expone en la Data API** (`config.toml` lista `public` y `graphql_public`): se llega por los RPC.

```sql
select sync.push(jobs, device_id);                       -- ingesta batch
select sync.pull(entidades, watermark, limite, device);  -- delta (el alcance se ignora desde 0023)
select sync.estado();                                    -- telemetría del colportor (RF-SY06)
```

Tres cosas que conviene saber antes de tocarlo:

**La RLS es la autoridad de permisos, también en el push.** Los RPC son `SECURITY INVOKER` y no reciben el usuario por parámetro: lo sacan de `auth.uid()`. El BFF reenvía el JWT y no decide nada ([ADR-013](https://github.com/Colportores/docs-organizacion/blob/main/docs/decisiones/ADR-013-un-bff-por-aplicacion-en-workers.md)). Por eso no hay filtro manual por columna de dueño — un `select` dentro de estas funciones ya devuelve solo lo que el usuario puede ver, y eso cubre los tres casos que un filtro por columna no cubría: `venta_item`/`entrega`/`cobranza` (sin columna propia, heredan el permiso vía `venta`), las tablas compartidas por ciudad (`mis_ciudades_de_trabajo()`, que no es una igualdad) y los catálogos globales.

**El cursor del delta es el xid de la transacción, no el reloj.** `updated_at` se llena con `now()`, que es la hora de *inicio* de transacción: dos escritores concurrentes commitean en un orden que no tiene por qué coincidir con el de sus timestamps, y la fila que commiteó tarde queda detrás de un watermark que ya avanzó — subida, guardada y jamás entregada. Se ordena por `(xmin_w, id)` y se sirve solo lo que está por debajo de `pg_snapshot_xmin(pg_current_snapshot())`. El diagnóstico y el arreglo son de @BrunoFCapri.

**`xmin_w` lo pone el trigger de auditoría, no el RPC.** Si dependiera del RPC, toda escritura que no pase por `sync.push()` —seeds, panel del coordinador, un job— dejaría la fila con el xid de su INSERT: modificada en la base y nunca propagada.

**Las políticas RLS envuelven sus llamadas en `(select ...)`.** `tiene_rol()` suelta en un `USING` se evalúa **por fila**; envuelta es un InitPlan que corre una vez. Medido sobre 390.000 filas, el delta de `ubicacion` pasó de **1.210 ms a 35 ms** (`supabase/bench/README.md`). Un test en `0002_rls_test.sql` falla si una política nueva se aparta.

El registro de entidades (`sync.entidad`) es una tabla y no una lista en el código: el RPC es genérico, y sin lista blanca un cliente podría mandar `entity: "usuario"` y escribir donde no debe. Es el espejo en SQL del `SyncSpec` del motor ([contrato §2](https://github.com/Colportores/docs-organizacion/blob/main/docs/contrato-sync-engine.md)). **`persona` y `nota` no están, y no van a estar.**

**Último dato recibido por colportor** (`0053`, backend-supabase#93, HU-CAM-008, vista 31 «Inicio», C2 de [docs#69](https://github.com/Colportores/docs-organizacion/issues/69), supuesto S61). `usuario.ultimo_push_at` guarda cuándo el servidor recibió el último `sync_push` de ese usuario; `null` si todavía no llegó ninguno (el panel muestra «sin datos»). Es un dato visual del «tiempo sin conexión»: sin umbral, sin color y sin alerta, y sin nada de los clientes. `public.sync_push()` lo actualiza (por `sync.registrar_push_recibido()`, `SECURITY DEFINER`, en el schema `sync`) cuando el lote pasó la puerta, sea cual sea el resultado de sus jobs (accepted, duplicate, conflict o invalid: el teléfono estaba conectado); un lote que la puerta rechaza (CS001 a CS003, 42501), un pull y un `sync.push()` llamado directo no cuentan. Nunca retrocede y no reescribe la fila si ya está en `now()`. Solo la escribe el servidor: un trigger descarta, sin error, un valor que mande `authenticated` o `anon` en un UPDATE de su propia fila (como la suspensión, `0004`). La lectura del tablero (backend-supabase#94) la devuelve; `usuario` sigue siendo legible solo por el propio usuario y el ADMIN. Cada push sube el `updated_at` y la `sync_version` de la fila de `usuario`, que no está en `sync.entidad`: no baja ni invalida nada.

## Estado de la cuenta

`select public.estado_cuenta();` devuelve el estado del usuario autenticado: `ACTIVA`, `PENDIENTE_ASIGNACION` o `SUSPENDIDA` (HU-AUTH-008). Lo consume `bff-colportores` en `GET /v1/me` con el JWT del usuario ([ADR-013](https://github.com/Colportores/docs-organizacion/blob/main/docs/decisiones/ADR-013-un-bff-por-aplicacion-en-workers.md)); por PostgREST es `POST /rest/v1/rpc/estado_cuenta` y responde un string JSON.

**No es una columna que alguien mantenga**, se deriva:

- `SUSPENDIDA` si `usuario.suspendido_en` no es null. Gana sobre todo lo demás.
- `ACTIVA` si tiene una inscripción vigente en `campania_colportor`: fila no borrada, campaña no borrada y hoy (el día de Montevideo, `0024`) entre `fecha_inicio` y `fecha_fin`. Cuando HU-CAM-004 inscribe al colportor en una campaña en curso, la cuenta queda activa sola; si la inscribe en una **por empezar** (`0058`), sigue `PENDIENTE_ASIGNACION` hasta que la campaña empiece (pendiente de decisión).
- `PENDIENTE_ASIGNACION` en cualquier otro caso.

"Vigente" está escrito una sola vez, en `mis_campanias_vigentes()`, y `mis_zonas()` lo usa. Con una diferencia: una inscripción sin zona activa la cuenta, pero no abre ninguna zona.

`suspendido_en` la fija el servidor: un trigger descarta en silencio cualquier cambio que venga con JWT, incluido el de un ADMIN. Quién suspende y reactiva es de HU-ADM-003, que todavía no está decidido.

### Términos y Política de Privacidad aceptados

Al registrarse, la persona acepta los Términos y la Política de Privacidad (HU-AUTH-001, R-AU04, Ley 18.331) y el servidor guarda **qué versión** aceptó y **cuándo** (`0065`). Una fila por (usuario, versión) en `public.consentimiento_terminos`: un historial, para que la v2 sume una fila y la v1 quede como prueba.

- **Cómo llega:** el móvil manda la versión en los metadatos del registro, `signUp(data: {'terminos_version': 'v1'})` (front-colportores-mobile#386). El trigger que crea el perfil (`tg_auth_usuario_nuevo`) crea también la fila, con la hora del servidor: ni la fecha ni el usuario salen del cliente.
- **Forma y versiones publicadas:** `v1`, `v2`… (`^v[1-9][0-9]{0,8}$`), la de la dirección del documento, y además tiene que ser una versión **publicada**: hoy solo `v1`, con la lista en un solo lugar, `public.terminos_versiones_publicadas()`. Una versión nueva se suma ahí, con su migración, cuando se publica su texto. Sin la clave (o con null) el registro sigue igual y no se guarda nada; con otra forma, o con la forma correcta pero no publicada (`v7`), el registro se rechaza con `TC001`.
- **Quién lo ve:** cada persona lee solo lo suyo (`select` por la API, `consentimiento_terminos`); nadie lo escribe con su JWT, ni un ADMIN. Lo escribe el trigger del registro o el servidor (`service_role`). No está en `sync.entidad`: no baja al teléfono.
- Las cuentas que ya existían quedan sin fila: no se inventa qué aceptaron.

## Inscripción en campaña

`select public.inscribir_colportor(campania_id, usuario_id);` inscribe a un colportor en una campaña y devuelve la fila de `campania_colportor` (HU-CAM-004). Con eso su cuenta pasa sola de `PENDIENTE_ASIGNACION` a `ACTIVA`. Lo consume `bff-coordinadores`; por PostgREST es `POST /rest/v1/rpc/inscribir_colportor`.

- **Quién.** El coordinador de esa campaña (`campania.coordinador_id`) o un ADMIN. Si no, `42501`.
- **Qué reglas.** Campaña que no terminó (en curso o **por empezar**, desde la `0058`: se puede sumar al equipo antes del inicio, backend-supabase#103, decisión de Cristian del 21/10); usuario existente, con email verificado y no suspendido; que no esté ya inscripto; que no esté en otra campaña del mismo momento (dos en curso o dos por empezar; una en curso y otra por empezar sí, R-CM02). Cada regla tiene su código propio, `CI001`..`CI007`: ver el header de la migración `0005` (desde la `0028` no existe `CI008`: una inscripción dada de baja se reactiva, ver más abajo). No se mira el rol de la persona: un coordinador o un ADMIN se inscriben como colportores en otra campaña igual que cualquiera (decisión de Cristian, 02/10).
- **Reactivar.** Si la persona tiene una inscripción dada de baja en **esa misma campaña**, `inscribir_colportor()` la reactiva (backend-supabase#41, migración `0028`, decisión de Cristian del 02/10): devuelve la misma fila (mismo `id`, `created_at`, `created_by` y `meta_libros`) con `deleted_at = null` y **sin zona**, y no crea otra. Las reglas de arriba valen igual (campaña vigente, cuenta no suspendida, sin otra campaña vigente). En `buscar_candidatos()` la persona que el coordinador quitó aparece con `motivo_bloqueo = null`: ya no hay motivo `INSCRIPCION_BORRADA`.
- **Dónde viven.** Una sola definición, `motivo_rechazo_inscripcion()`, que es interna.
- **Un solo camino.** El RPC es el único camino para inscribir con JWT. `campania_colportor` no tiene política INSERT, así que la RLS niega el INSERT directo, incluso al ADMIN. El RPC es `SECURITY DEFINER` y toma un lock por usuario: así nadie queda en dos campañas vigentes por dos inscripciones simultáneas.
- **Qué no se puede hacer con un UPDATE.**
  - Cambiar la campaña o el usuario de una inscripción. Reasignar es cerrar una y abrir otra (HU-CAM-005).
  - Reactivar una inscripción borrada. Se hace con `inscribir_colportor()`, que revisa el permiso, la suspensión y la otra campaña: un UPDATE con JWT que pase `deleted_at` a `null` se rechaza con `23514` (el servidor, sin JWT, sí puede: seeds y jobs).

### Cuentas: qué ve el coordinador y búsqueda de candidatos

Desde la migración `0015` (backend-supabase#41) el coordinador **no lee `public.usuario` directo**: la política `usuario_select_propio_o_admin` le deja leer solo su fila (la del `GET /v1/me`); el ADMIN lee todas. A las cuentas ajenas llega por dos RPC, que acotan filas y columnas (decisiones de Cristian del 30/09, front-coordinadores-web#20 y #29):

```sql
select * from public.colportores_de_campania(campania_id);        -- «Ya en tu equipo»: nombre, email y estado
select * from public.buscar_candidatos(campania_id, texto, despues_de); -- vista 23: sugeridos o búsqueda
```

- **Quién.** El coordinador de esa campaña o un ADMIN, con la campaña sin terminar (en curso o por empezar, `0058`). Si no, `42501`; `buscar_candidatos()` responde `CI001`/`CI002` (terminada) como `inscribir_colportor()`.
- **Candidatas.** Cuentas vivas, con el email verificado y que no estén ya en el equipo. Aparecen también las suspendidas y las que están en otra campaña del mismo momento, con su `motivo_bloqueo`: el motivo con que `inscribir_colportor()` las rechazaría (`null` si se pueden añadir). Desde la `0028` la persona que el coordinador quitó de esta campaña aparece con `motivo_bloqueo = null`: «Añadir» reactiva su inscripción.
- **Sin texto: sugeridos.** Hasta 5 cuentas `PENDIENTE_ASIGNACION`, de la más nueva a la más vieja.
- **Con texto: búsqueda.** Las cuentas cuyo nombre completo o email contiene el texto, sin distinguir mayúsculas ni tildes. Primero las que empiezan con él (nombre, apellido o email); después el resto, alfabético (decisión del 02/10). De a 10 por página: para la siguiente, `despues_de` es el `usuario_id` de la última cuenta mostrada (cursor, sin duplicados ni huecos aunque la lista cambie entre páginas). Una página con menos de 10 es la última.
- **Columnas.** `usuario_id`, `nombre`, `apellido`, `email`, `estado` (como `estado_cuenta()`), `campania_actual` (la campaña vigente en la que está, para «Está en campaña X»), `creada_en` y `motivo_bloqueo`.
- **Estado de la cuenta.** La precedencia (suspendida, activa, pendiente) vive en `estado_de_cuenta()`, que usan `estado_cuenta()` y los dos RPC.

### Zona del colportor

`select public.asignar_zona(campania_id, usuario_id, zona_id);` asigna o cambia la zona de un colportor inscripto (`campania_colportor.zona_id`, HU-CAM-006) y devuelve la fila. `mis_zonas()` le abre la zona nueva y deja de abrirle la anterior.

Desde la migración `0009`, la inscripción es el **único** lugar donde vive la zona de un colportor (`null` = sin zona): `usuario.zona_id` ya no existe. Un trigger (`campania_colportor_zona_valida`) exige, también fuera del RPC, que la zona sea de una ciudad viva de la misma campaña y no esté dada de baja; lo revisa también al reactivar una inscripción dada de baja (si su zona ya no sirve, se rechaza y el aviso dice que se reactive sin zona; desde `0022`, dar de baja una inscripción la deja sin zona, así que eso solo alcanza a las que ya estaban de baja con zona). `mis_zonas()` solo devuelve zonas vivas de inscripciones vigentes.

- **Quién.** El coordinador de esa campaña o un ADMIN. Si no, `42501`.
- **Qué reglas.** Campaña que no terminó (en curso o por empezar, desde la `0058`; `CZ002` es la terminada); colportor con inscripción viva en esa campaña; zona viva de una ciudad de esa campaña (desde `0008`: `CZ006` si es de otra campaña, `CZ005` si su ciudad se quitó de la campaña). Los códigos son `CZ001`..`CZ006`: ver el header de las migraciones `0006` y `0008`.
- **Un solo camino.** Es el único camino para cambiar `zona_id` con JWT: un trigger rechaza el UPDATE directo de esa columna, incluso del ADMIN.
- **Con quién comparte el permiso.** El chequeo de permiso y campaña sin terminar (`motivo_campania_del_coordinador()`) es el mismo que usa `inscribir_colportor()`, `buscar_candidatos()` y `quitar_zona()`.
- **Historial de zonas** (`0022`, decisión del 02/10). `campania_colportor.zona_id` sigue siendo la zona actual; además `campania_colportor_zona_historial` guarda un tramo por zona (`desde`, `hasta`, quién la asignó en `created_by` y quién la cerró en `cerrada_por`), para auditoría. Lo llena solo un trigger de `campania_colportor`, al asignar, cambiar, quitar o dar de baja la zona, o al dar de baja la inscripción; no hay nada que llamar. **Dar de baja la inscripción** deja al colportor sin zona (decisión de Cristian, 02/10): el tramo se cierra con quién y cuándo, y al volver (reactivación) aparece en «Sin zona» hasta que se le asigne otra con `asignar_zona()`. Si se elimina al usuario que asignó o cerró un tramo, `created_by` y `cerrada_por` quedan en `null`. El tramo vigente tiene `hasta` en `null`. Los tramos que ya existían al activarlo van con `inicial = true`: su `desde` es el de la migración, no el de la asignación real. Lo leen el ADMIN y el coordinador de la campaña (`select … from campania_colportor_zona_historial where campania_colportor_id = …`); nadie lo escribe directo y no baja al teléfono (no va por el pull ni por el push).

## Precio de venta: general y modificado por ciudad

Desde la migración `0034` (backend-supabase#78, decisión de Cristian del 06/10, «Precio gral.»): **Administración pone un precio general** para todo el país y la coordinadora puede **modificarlo para una ciudad de su campaña**. Vale el modificado vigente y, si no hay, el general.

```sql
select * from public.precio_vigente(campania_ciudad_id, producto_id);                       -- hoy
select * from public.precio_vigente(campania_ciudad_id, null, coleccion_id, '2026-03-01');  -- una colección, en otra fecha
```

Para **listar** los precios de una ciudad de la campaña de una sola vez (la vista 27 del panel, sin llamar a `precio_vigente()` producto por producto), desde la migración `0037` (backend-supabase#84):

```sql
select * from public.precios_de_la_ciudad(campania_ciudad_id);                -- hoy
select * from public.precios_de_la_ciudad(campania_ciudad_id, '2026-03-01');  -- los de otro día
```

- **Dos tablas.** `precio_general` (nueva: producto o colección, centavos, `valido_desde` / `valido_hasta`, un solo vigente a la vez) y `precio_por_ciudad`, que no cambió y son las modificaciones. Cada tramo de precio es una fila: ese es el historial. Un precio nuevo vale para las ventas que se registren después; las anteriores conservan el suyo en `venta_item.precio_unitario`.
- **Qué devuelve `precio_vigente()`.** Una fila con `origen` (`MODIFICADO` o `GENERAL`), `precio_id`, `precio_venta`, `valido_desde` y `valido_hasta`, o ninguna si no hay ni modificado ni general vigente (el producto no se ofrece en esa ciudad). Sin fecha usa el día de Montevideo (`hoy_montevideo()`, no el `current_date` de la sesión) y las dos fechas del tramo valen. Se pasa el producto **o** la colección (22023 si no).
- **Qué devuelve `precios_de_la_ciudad()`** (`0037`). Una fila por cada producto y cada colección **vivos** del catálogo, tenga precio o no: `tipo` (`PRODUCTO` o `COLECCION`), `id`, `nombre`, `es_bonificable` (null en una colección), `precio_general`, `precio_modificado` (el de esa ciudad de la campaña), `precio_vigente` (el modificado si lo hay y, si no, el general), `origen` (`MODIFICADO` o `GENERAL`) y la vigencia de ese precio (`valido_desde`, `valido_hasta`). Un producto sin ningún precio sale con todo en null: no se ofrece en esa ciudad, y los bonificables en ese caso son la alerta «Productos bonificables sin precio en X». Importes en centavos; productos antes que colecciones, por nombre; sin tope. La fecha es opcional (por defecto, el día de Montevideo). No tiene historial: es lo que rige en esa fecha.
- **Quién la llama.** El **ADMIN** y el coordinador **de esa campaña**, también si la campaña ya terminó o todavía no empezó. Un colportor (lee por el sync), un coordinador de otra campaña, un usuario sin rol o sin sesión reciben `42501`; una ciudad que no existe o se quitó de la campaña, `CZ012`; una campaña que no existe o está dada de baja, `CZ001`. Es `SECURITY DEFINER` con el permiso primero, `STABLE`, y `EXECUTE` solo para `authenticated`.
- **Quién.** Escribe el general solo el **ADMIN** (no hay `DELETE`: la baja es `deleted_at`). Lo lee el ADMIN y quien hoy lee los precios de una campaña (el coordinador que la lleva y el colportor inscripto en una que no terminó); un colportor sin campaña no lo lee. `precio_vigente()` es `SECURITY INVOKER`: la RLS sigue siendo la autoridad, y una ciudad de campaña que el usuario no ve no devuelve nada. `EXECUTE` solo para `authenticated` y `service_role`.
- **Todavía no.** El general no se sincroniza al teléfono ni se publica por Realtime: eso cambia el contrato de sync y la publicación de Realtime ([ADR-012](https://github.com/Colportores/docs-organizacion/blob/main/docs/decisiones/ADR-012-backend-supabase-sa-east-1.md)), y va en un PR de docs aparte que revisa Bruno. Tampoco existe la pantalla de Administración: hasta entonces se carga con el seed y con [`docs/guia-carga-manual.md` § 8](./docs/guia-carga-manual.md).

## Combos: una colección con precio propio

Desde la migración `0056` (backend-supabase#99, HU-CAT-009 y HU-VEN-001, decisión de Cristian del 21/10, C10): un **combo** es una `coleccion` de productos con **su propio precio** y se vende como **un solo ítem**.

- **El precio** es el de cualquier producto: `precio_general` (todo el país) y `precio_por_ciudad` (excepciones) aceptan `coleccion_id` desde la `0027`/`0034`, y `precio_vigente(campania_ciudad, null, coleccion_id)` y `precios_de_la_ciudad()` (`tipo = 'COLECCION'`) lo resuelven. El precio del combo no sale de sumar los componentes. Sin precio general ni excepción en la ciudad, no se ofrece. Si un componente se da de baja, el combo deja de ofrecerse hasta corregirlo: lo decide el teléfono con el pull (`producto.deleted_at` y `producto_coleccion`), el servidor nunca rechaza una venta por el catálogo, y `precios_de_la_ciudad()` (desde la `0057`) trae `componentes_de_baja` (cuántos componentes vivos del combo son productos dados de baja; 0 si ninguno) sin quitarle el precio, para que el panel avise qué combos quedaron afectados.
- **Los componentes** son `producto_coleccion` con su `cantidad` (entero `> 0`, `1` por defecto): «1 libro y 2 revistas» son dos filas. Un combo no puede incluir otro combo: `producto_id` es una FK a `producto`.
- **La venta.** `venta_item` lleva `producto_id` **o** `coleccion_id` (exactamente uno, `23514` si vienen los dos o ninguno) con `cantidad`, `precio_unitario` (la foto del precio del combo) y `subtotal`. El teléfono lo sube por `sync_push` como cualquier ítem. La venta no se rechaza por el estado del catálogo: se hizo sin conexión y nunca se pierde.
- **Todavía no.** El stock de cada producto del combo se descuenta en V2 (HU-STK-007, necesita la tabla `stock`). Hasta que exista la pantalla de Administración los combos se arman a mano con [`docs/guia-carga-manual.md` § 7b](./docs/guia-carga-manual.md); `supabase/seed.sql` trae «Pack Familiar de Ejemplo».

## Mapa de la campaña

Una campaña abarca una o más ciudades (`campania_ciudad`) y cada ciudad se divide en zonas dibujadas sobre el mapa (vista 24 del panel, migración `0008`). Una zona es `RADIAL` (centro y radio; el polígono lo calcula el servidor) o `ESQUINAS` (esquinas en `zona_vertice` y el borde que sigue las calles, que llega ya calculado). `zona.poligono_geojson` es la geometría que dibujan la app y el panel.

```sql
select public.agregar_ciudad_a_campania(campania_id, ciudad_id);   -- «+ Agregar ciudad»
select public.guardar_zona(campania_ciudad_id, nombre, tipo_forma, color, centro_lat, centro_lon,
                           radio_m, vertices, poligono_geojson, zona_id, vista_previa);
select public.baja_zona(zona_id, vista_previa);                     -- «Eliminar zona»
select public.quitar_zona(campania_id, usuario_id);                -- «Quitar» (0012)
```

- **Quién.** El coordinador de la campaña o un ADMIN, y solo si la campaña no terminó. Nadie escribe estas tablas directo (ni el privilegio tiene `authenticated`).
- **Superposición.** Las zonas se pueden superponer (S56, migración `0013`): no hay regla ni tolerancia, y nada se rechaza por tocar o cubrir parte de otra zona (desde `0038` se avisa: ver «Avisos de la vista previa»). El nombre sí es único entre las zonas vivas de la misma `campania_ciudad` y tiene hasta 40 caracteres, sin contar los espacios de los costados (`CZ009`; el tope es de `0024`, HU-CAM-006).
- **Forma.** `RADIAL`: radio de 1 a 3000 m (hasta ahí el círculo de 128 lados queda a menos de 1 m del geodésico). `ESQUINAS`: al menos 3 esquinas en lugares distintos (a 1 m o menos cuentan como la misma), con `orden` entero, y el borde pasando a 1 m o menos de cada una. Todo lo demás, `CZ008`.
- **Vista previa.** Con `vista_previa` no se guarda nada: devuelve el polígono y `ubicaciones_incluidas`, el «Incluye N ubicaciones» de la vista 24: las ubicaciones vivas de la ciudad que caen dentro de la forma, calculado en el momento con PostGIS. Al guardar devuelve lo mismo. `baja_zona()` devuelve las que incluía la zona. Guardar o dar de baja una zona no toca ninguna ubicación.
- **Avisos de la vista previa** (`0038`, backend-supabase#87, HU-CAM-006). La respuesta de `guardar_zona()`, en la vista previa y al guardar, suma dos claves; **nunca rechazan** el guardado.
  - `superposiciones`: `[{zona_id, nombre, interseccion}]`, una por zona **viva** de la **misma ciudad de la campaña** que comparte **área** con la zona que se dibuja; `interseccion` es la parte común en GeoJSON (el tramo en rojo de la vista 24). Sin tolerancia en metros: dos zonas que solo comparten el borde (o un punto) no se superponen. Editar una zona no la superpone consigo misma (`p_zona_id`); las zonas dadas de baja, las de otra ciudad de la campaña y las de otra campaña no cuentan. Por nombre y id; `[]` si no hay.
  - `calles_compartidas`: el aviso «Comparte la calle Heredia con Belvedere» del canvas 24, solo para una zona `ESQUINAS` (una `RADIAL` devuelve `[]`). `[{zona_id, nombre, calle, punto}]`: la zona vecina, la calle y un punto del tramo para el rótulo (GeoJSON `Point`). Comparte cuando el borde nuevo recorre al menos **un tramo** de la red de calles (`ruteo.tramo`) que también está en el borde de otra zona viva de la misma ciudad de la campaña. «El borde nuevo recorre» un tramo cuando ese tramo es parte **del camino por calles entre las esquinas** (el mismo que arma `poligono_por_calles()`, desde `0059`, backend-supabase#91) y además queda entero a 1 m o menos del borde de la zona vecina (el metro de las esquinas, ADR-018): un tramo que sale del borde, aunque mida menos de 1 m o corra pegado a él, no es una calle que la zona recorra y no se avisa. Sin largo mínimo (un tramo corto que sí es parte del camino cuenta), y tocarse en una sola esquina no cuenta (tampoco un tramo que queda entero a 1 m o menos de un punto donde los dos bordes se tocan o se cruzan). Una fila por zona y por calle; si el tramo no tiene nombre en OSM, `calle` es `null`. Compartir una calle **no** es superponerse. `null` (no `[]`) si la ciudad todavía no tiene calles cargadas, si el camino entre las esquinas no se puede armar (hay menos de 3 cruces distintos entre ellas o no hay camino por las calles entre dos esquinas seguidas) o si hay una recarga de las calles en curso: no se pudo calcular, y el guardado sigue igual.
  - Permiso: el de `guardar_zona()` (el coordinador de la campaña o un ADMIN). Lo que devuelve son nombres de zona, geometría y nombres de calle: ni importes ni personas. Las dos funciones que lo calculan (`zonas_que_se_superponen()`, `zonas_que_comparten_calle()`) son internas: sin `EXECUTE` para `anon` ni `authenticated`.
- **Baja y «Quitar».** La baja es lógica. Los colportores asignados quedan sin zona y devuelve quiénes (`colportores_asignados`) y cuántos (`colportores_sin_zona`), también en la vista previa (`0012`). `quitar_zona()` deja sin zona a un colportor. `asignar_zona()` rechaza una cuenta suspendida (`CZ014`), que conserva la zona que tenía.
- **Lectura.** El colportor ve las ciudades, zonas y esquinas de toda campaña en la que está inscripto y que **no terminó**: en curso o por empezar (todas las zonas, no solo la suya; S56, `0013`, y decisión del 30/09: el mapa de una campaña futura se baja antes del primer día). Las terminadas, no. El coordinador ve las de las campañas que coordina, terminadas incluidas; el ADMIN, todas. `campania_ciudad`, `zona` y `zona_vertice` viajan por el delta como pull, y su watermark lleva la huella de las campañas que ve (`sync.entidad.sigue_campanias`). Si cambian (termina una campaña, lo inscriben o lo reactivan), el mapa baja completo, también lo que se cargó antes de su último pull. El servidor no manda borrados: el mapa de una campaña terminada queda en el teléfono y la app decide si lo muestra.
- **La inscripción en el celular.** `campania_colportor` baja por el pull (`0014`), solo con las inscripciones propias: `sync.entidad.columna_duenio` filtra por `usuario_id = auth.uid()` aunque la RLS le muestre más al coordinador o al ADMIN. Con eso la app sabe su campaña y su zona, y recibe el cambio cuando se la asignan, se la quitan o dan de baja la zona. La app no la escribe (`ENTIDAD_DE_SOLO_LECTURA`).
- **Códigos.** `CZ008`..`CZ014`: ver los headers de las migraciones `0008` y `0012`. `CZ007` (superposición) y `CZ010` (baja con asignados) ya no se usan.

### Lecturas del panel (sin BFF)

Desde la migración `0033` (backend-supabase#54, [ADR-013](https://github.com/Colportores/docs-organizacion/blob/main/docs/decisiones/ADR-013-clientes-directo-a-rpc-de-supabase.md)) el panel de coordinadores lee con cinco RPC y nunca con `.from()`. Lo que antes armaba `bff-coordinadores` con `select` es ahora esto (la forma de cada respuesta es el contrato del panel, `src/datos/shell/contrato.ts` y `src/datos/equipo/zonas/contrato.ts` en `front-coordinadores-web`):

```sql
select * from public.mi_perfil();                                    -- topbar: usuario_id, nombre, apellido
select * from public.campanias_del_coordinador();                    -- mis campañas que no terminaron: el campania_id
select * from public.ciudades_de_campania(campania_id);              -- las pestañas de la vista 24
select * from public.ciudades_del_catalogo(campania_id, texto);      -- el buscador de «+ Agregar ciudad»
select * from public.zonas_de_ciudad(campania_id, campania_ciudad_id); -- las zonas de una pestaña
```

- **Quién.** Se llaman con el JWT del usuario. Sin sesión, un colportor, un usuario sin rol o con el rol vencido: `42501`, antes de mirar ninguna campaña (un colportor tampoco averigua qué campañas existen). Las tres de campaña piden además ser el coordinador de esa campaña (o un ADMIN), con la misma comprobación que las escrituras del mapa (`exigir_lectura_de_campania()` → `motivo_mapa_de_campania()`): una campaña en curso o **por empezar** se lee (la vista 24 prepara el mapa antes del inicio); una **terminada**, `CZ011`; inexistente o dada de baja, `CZ001`. El coordinador de otra campaña que existe recibe `42501`, y si no existe, `CZ001` (la existencia se mira antes que el dueño, igual que en `guardar_zona()`; con ids UUIDv7 no se puede sondear qué campañas hay); la vigencia va después del permiso, así que una campaña ajena y terminada también da `42501`. `zonas_de_ciudad()` exige además una ciudad viva de esa campaña: si no, `CZ012`, sea de otra campaña, inexistente o quitada.
- **Qué devuelven.** `campanias_del_coordinador()`: las campañas vivas que coordina quien llama y que no terminaron (el día se cuenta en Montevideo y el último día todavía cuenta): `id`, `nombre`, `tipo`, `fecha_inicio` y `fecha_fin`, primero las en curso (la que empezó más tarde, primero) y después las por empezar (la más próxima, primero); el `id` es el `p_campania_id` de las otras tres, y un ADMIN ve solo las que coordina él. `ciudades_de_campania()`: por ciudad viva, `campania_ciudad_id` (el id de la pestaña, el que recibe `guardar_zona()`), `ciudad_id` (el del catálogo, el que recibe `agregar_ciudad_a_campania()`), `nombre`, `departamento` (desde la `0066`; `null` = ciudad cargada antes, todavía sin departamento: una ciudad nueva no se carga sin él y no se le puede borrar a una que lo tiene, `CD001`), `lat_centro`, `lon_centro`, `zoom_inicial` y `cantidad_zonas` (las vivas). `ciudades_del_catalogo()`: `ciudad_id`, `nombre` y `departamento` de las ciudades vivas del catálogo que no están en la campaña, las cuyo nombre **o departamento** contienen el texto sin distinguir mayúsculas ni tildes (primero las cuyo nombre empieza con él, después A-Z por nombre y, a igual nombre, por departamento: dos «San José» salen cada una con el suyo; sin texto, todas; el texto es literal, `%` y `_` no son comodines). `zonas_de_ciudad()`: por zona viva, su forma (`tipo_forma`, `color`, `centro_lat`, `centro_lon`, `radio_m` si es RADIAL; `esquinas`, un jsonb `[{orden, lat, lon, calle_a, calle_b}]`, si es ESQUINAS), `poligono_geojson`, `colportores` (jsonb `[{usuario_id, nombre, apellido, suspendido}]` de las inscripciones vivas con esa zona) y `ubicaciones_registradas` (cuántas ubicaciones vivas de la ciudad caen adentro, la misma cuenta que «Incluye N ubicaciones»). Tres `null` que el adaptador del panel tiene que cubrir: `departamento` (una ciudad cargada antes de la `0048` y todavía sin él; la base no lo exige aún, [guía de carga](./docs/guia-carga-manual.md) § 2), `zonas_de_ciudad().color` (una zona se puede guardar sin color) y `esquinas[].calle_a` / `calle_b` (los polígonos que se convirtieron a ESQUINAS no tienen calles).
- **Qué no devuelven.** Ni email, ni ubicaciones, ni espacios, ni personas, ni visitas, ni ventas: de las ubicaciones, un número. Ninguna escribe.
- **Cómo.** `mi_perfil()` y `campanias_del_coordinador()` son `SECURITY INVOKER` y `STABLE` (la RLS de `usuario` deja leer la fila propia; `campania` es de lectura abierta y la función filtra por `coordinador_id = auth.uid()`); las otras tres son `SECURITY DEFINER` con `search_path` vacío y columnas explícitas, porque el coordinador no lee `usuario` ajeno. `EXECUTE` solo para `authenticated`. Las tres de campaña son `VOLATILE` (llaman a `lanzar_motivo_mapa()`): `supabase-js` las manda por `POST`.
- **Las otras dos lecturas de la vista 24.** `colportores_de_campania()` y `zonas_asignables()` (de `0007`/`0015`) se recrean en la `0033` con el mismo criterio de lectura (`exigir_lectura_de_campania()`): una campaña en curso o **por empezar** contesta con su lista (en una por empezar los colportores son los que se sumaron antes del inicio, `0058`), una **terminada** da `CZ011` (antes `CZ002`) e inexistente `CZ001`. `inscribir_colportor()` y `asignar_zona()` no cambiaron en la `0033`; los cambió la `0058` (abajo en «Qué reglas» de cada una): piden una campaña que no terminó, no una que ya empezó.
- **Pendiente de decisión.** La `provincia` del catálogo (HU-CAM-006 la pide; `public.ciudad` no tiene esa columna) y cómo conoce el panel su `campania_id`: ver el header de la migración `0033`.

### Casas de una zona para el panel (sin BFF)

Desde la migración `0039` (backend-supabase#72, decisiones de Cristian del 06/10, «Puntos panel» y «Cobro panel», [ADR-003](https://github.com/Colportores/docs-organizacion/blob/main/docs/decisiones/ADR-003-cache-house-status-del-mapa.md)) el panel pinta en la vista 24, sobre las calles, los puntos de las casas de una zona con su estado. Una RPC, que el panel llama directo ([ADR-013](https://github.com/Colportores/docs-organizacion/blob/main/docs/decisiones/ADR-013-clientes-directo-a-rpc-de-supabase.md)):

```sql
select * from public.casas_de_zona(campania_id, zona_id);                          -- la primera página (hasta 1000)
select * from public.casas_de_zona(campania_id, zona_id, ultimo_ubicacion_id, 500); -- la siguiente, de a 500
```

- **Qué devuelve.** Una fila por ubicación **viva** de la ciudad de la zona que cae dentro de su forma (borde incluido: la misma cuenta que «Incluye N ubicaciones» y que `zonas_de_ciudad().ubicaciones_registradas`; la zona es solo visual): `ubicacion_id`, `lat`, `lon`, `tipo` (`CASA`, `NEGOCIO` o `EDIFICIO`) y `estado`, el `color` de su `house_status`: los **siete** (`ENTREGA_Y_COBRANZA_PENDIENTE`, `COBRANZA_PENDIENTE`, `ENTREVISTA_PROGRAMADA`, `VENTA_COMPLETA`, `ENTREVISTA_SIN_VENTA`, `SIN_CONTESTAR` y `RECHAZO`), también los de cobranza pendiente y venta pagada. `estado` es `null` si la casa todavía no tiene `house_status` (o el suyo está de baja): el punto está y el panel decide cómo dibujarlo.
- **Qué no devuelve.** Ni personas, ni notas, ni visitas, ventas, cobranzas o importes, ni la dirección (se suma solo si el artboard de la vista 24 la pide, con [ADR-004](https://github.com/Colportores/docs-organizacion/blob/main/docs/decisiones/ADR-004-frontera-de-privacidad-en-la-persona.md)). Ninguna escribe.
- **Tope y paginado.** Orden fijo por `ubicacion_id`. `p_limite` (1 a 5000, 1000 por defecto) es el tamaño de la página; si vuelven `p_limite` filas puede haber más: la siguiente se pide con `p_despues_de` = el `ubicacion_id` de la última fila, y una página con menos filas que `p_limite` es la última. Un `p_limite` fuera de rango da `22023` (no se recorta en silencio). El cursor es una clave de orden: sigue andando si esa casa se dio de baja entre dos páginas. Con 300 mil ubicaciones en la ciudad, una página de 5000 tarda ~55 ms (índice GiST de `ubicacion_geometria`).
- **Quién.** Con el JWT del coordinador de la campaña (o un ADMIN), con el permiso de siempre de la vista 24 (`exigir_lectura_de_campania()`): sin sesión, colportor, sin rol, rol vencido o coordinador de otra campaña, `42501`, antes de mirar nada; campaña inexistente o de baja, `CZ001`; terminada, `CZ011` (una por empezar se lee). Después, `CZ004` si la zona no existe, está de baja o no es de una ciudad viva de esa campaña (una zona ajena y una inexistente contestan igual). `SECURITY DEFINER` con `search_path` vacío, `VOLATILE` (`supabase-js` la manda por `POST`), `EXECUTE` solo para `authenticated`.

### Horas por ciudad y colportor para el panel (sin BFF)

Desde la migración `0060` (backend-supabase#95, HU-REP-001, vista 32 «Reportes», decisión de Cristian del 21/10 «C3», [docs#69](https://github.com/Colportores/docs-organizacion/issues/69)) el panel lee las horas trabajadas por ciudad y por colportor, por día, semana o mes, con la tendencia contra el período anterior. Una RPC, que el panel llama directo ([ADR-013](https://github.com/Colportores/docs-organizacion/blob/main/docs/decisiones/ADR-013-clientes-directo-a-rpc-de-supabase.md)):

```sql
select * from public.horas_por_ciudad_y_colportor(campania_id, desde, hasta, 'semana');           -- 'dia' | 'semana' | 'mes'
select * from public.horas_por_ciudad_y_colportor(campania_id, desde, hasta, 'dia', ciudad_id);  -- una ciudad
select * from public.horas_por_ciudad_y_colportor(campania_id, desde, hasta, 'mes', null, array[colportor_id]);
```

- **Qué devuelve.** Una fila por período × ciudad × colportor: `periodo_inicio`, `periodo_fin`, `ciudad_id`, `ciudad_nombre`, `colportor_id`, `nombre`, `apellido`, `horas` (2 decimales), `jornadas`, `dias_trabajados` (para el promedio diario), `jornadas_acompaniadas`, `en_curso`, `horas_anterior` y `jornadas_anterior`. La ciudad que se expande a sus colportores la arma el panel sumando las filas; no hay subtotales. `jornadas = 0` quiere decir «sin datos ese período» (el panel lo muestra con guion y sin tendencia).
- **Qué cuenta.** Las jornadas **cerradas** (una sin `fin` no suma) de colportores inscriptos en la campaña, que empezaron entre su `fecha_inicio` y su `fecha_fin`; el día es el de `America/Montevideo`, y una jornada que cruza la medianoche cuenta entera en el día en que empezó. Cada colportor cuenta **desde el día de su inscripción en la campaña** (lo hecho antes, p. ej. en la campaña de la que lo reasignaron, es de la otra) y, si tiene baja, hasta ella: lo anterior a la baja sigue contando. La ciudad es la de la **zona actual** del colportor («Ciudad colp.», 21/10); sin zona (o con la zona o la inscripción de baja), `ciudad_id` y `ciudad_nombre` son `null`, **una sola vez** y no repetido en cada ciudad (repetirlo inflaría el total).
- **Período anterior.** Días: el día anterior (el de un lunes es el sábado). Semanas: la semana anterior. Meses: el mismo tramo del mes pasado (el mes en curso, los días 1 a hoy). Lo que está en curso (hoy, la semana en curso) **no se compara**: `horas_anterior` y `jornadas_anterior` son `null`; el mes en curso sí. Un período anterior sin jornadas da `0.00` y `0`. Una fila con `jornadas = 0` existe cuando el período anterior sí tiene datos, para que la suma de `horas_anterior` de una ciudad sea la de verdad. Los períodos futuros no salen.
- **El rango.** `desde` y `hasta` se redondean a períodos completos (la semana de lunes a domingo, el mes calendario) para que la punta no se compare cortada; en días no se redondea. Hasta 366 días ya redondeados: un rango más largo da `22023` (no se recorta en silencio). Peor caso medido (200 colportores × 365 días, 72 mil filas): ~1,6 s.
- **Qué no devuelve.** Ni clientes, ni visitas, ventas, importes o ubicaciones, ni el email, ni la hora de cada jornada: solo totales. Ninguna escribe.
- **Quién.** Con el JWT del coordinador de la campaña (o un ADMIN): sin sesión, colportor, sin rol, rol vencido o coordinador de otra campaña, `42501`, antes de mirar nada; campaña inexistente o de baja, `CZ001`; agrupación, fechas o rango inválidos, `22023`. A diferencia del mapa, **una campaña terminada se lee** (es cuando se liquidan los viáticos). `SECURITY DEFINER` con `search_path` vacío (el coordinador no lee `jornada`), `VOLATILE` (`supabase-js` la manda por `POST`), `EXECUTE` solo para `authenticated`.
- **Pendiente.** El filtro «departamento → ciudad» de la HU no se puede servir: `public.ciudad` no tiene `departamento` (ver `0033`). Depende de que las jornadas suban a la nube (backend-supabase#53): hasta entonces devuelve la lista vacía.

### Borde de las zonas por esquinas: las calles de OSM (sin BFF)

Desde la migración `0036` (backend-supabase#25, [ADR-018](https://github.com/Colportores/docs-organizacion/blob/main/docs/decisiones/ADR-018-geometria-de-zonas-y-ruteo-en-postgres.md), decisión de Cristian del 29/09) el borde de una zona `ESQUINAS` lo calcula la base con **pgRouting** sobre las calles de OpenStreetMap de la ciudad. El panel (vista 24) llama a tres RPC, sin BFF ([ADR-013](https://github.com/Colportores/docs-organizacion/blob/main/docs/decisiones/ADR-013-clientes-directo-a-rpc-de-supabase.md)), y a `guardar_zona()` le manda lo que devuelve la última. Guía completa, con cómo conseguir y actualizar las calles: [`docs/calles-ruteo.md`](docs/calles-ruteo.md).

```sql
select * from public.esquina_mas_cercana(campania_ciudad_id, lon, lat);   -- lon, lat, calle_a, calle_b, distancia_m
select * from public.tramo_por_calles(campania_ciudad_id, desde_lon, desde_lat, hasta_lon, hasta_lat);   -- orden, lon, lat
select * from public.poligono_por_calles(campania_ciudad_id, esquinas);   -- poligono_geojson, esquinas (con la forma de p_vertices)
```

- **Qué hacen.** `esquina_mas_cercana()`: el cruce de calles (un nodo donde se juntan al menos dos calles de nombre distinto) más cercano en metros, con las dos calles y a cuántos metros quedó; **sin tope de distancia**, `distancia_m` deja al panel decidir. `tramo_por_calles()`: el camino más corto por las calles entre las esquinas más cercanas a dos puntos, **sin respetar sentidos de circulación**. `poligono_por_calles()`: de 3 a 100 esquinas en el orden en que se marcaron, engancha cada una y pega los tramos (de la última a la primera: se cierra en la esquina 1); devuelve el `poligono_geojson` y las esquinas enganchadas, listos para `guardar_zona()`, que no cambia. Un borde que se cruza o vuelve sobre una calle: `CZ008`.
- **Quién.** Se llaman con el JWT del usuario y el permiso es lo primero, el mismo de `guardar_zona()`: sin sesión, un colportor, un usuario sin rol o con el rol vencido, o la campaña de otro coordinador: `42501`; la ciudad que no está en la campaña: `CZ012`; campaña inexistente `CZ001`, **terminada** `CZ011` (una **por empezar** sí, la vista 24 prepara el mapa antes del inicio). `SECURITY DEFINER` con `search_path` vacío, `VOLATILE`, `EXECUTE` solo para `authenticated`. Devuelven solo posiciones y nombres de calles.
- **Las calles.** Schema `ruteo` (`red`, `nodo`, `tramo`): fuera de la API, sin grants para `anon` ni `authenticated`, con RLS y sin políticas, y fuera del sync. Son datos de OSM (ODbL), no una entidad del dominio. Se cargan **por ciudad** con `bash scripts/db-importar-calles.sh <ciudad_id> <archivo.json>` (el JSON de Overpass con geometría; el repo no descarga nada) y se actualizan reimportando: `ruteo.cargar_red()` reemplaza la red entera en una transacción, o falla sin tocar nada. Entran las vías `trunk` a `residential`, `living_street`, `pedestrian` y `road`; no `service` ni senderos. Las zonas ya guardadas no cambian al reimportar. Una ciudad sin calles cargadas contesta `CZ015`; dos esquinas en partes de la red que no se tocan, `CZ016`.
- **pgRouting 3.4** viene en la imagen de Supabase (`create extension pgrouting with schema extensions`). No funciona con `search_path` vacío: solo `ruteo.dijkstra()` (una envoltura interna con `search_path = extensions`) lo necesita.
- **Decidido el 16/10.** Las calles de OSM se cargan a mano, una vez por ciudad, con el script (Overpass), en el paso de la ciudad de la [guía de carga](./docs/guia-carga-manual.md); el aviso «Comparte la calle X con Y» de la vista 24 sale de la vista previa de `guardar_zona()` (`0038`, backend-supabase#87: ver «Avisos de la vista previa»); los criterios (sin tope de distancia, tope de 100 esquinas, tipos de calle) quedan como están.

### Qué ubicaciones baja cada colportor

Desde la migración `0011` (backend-supabase#32, decisión D2 del 29/09) la zona es una guía visual: **las ubicaciones no guardan zona ni campaña** (`ubicacion.zona_id` y `house_status.zona_id`, de `0010`, ya no existen). La zona decide qué casas bajan al teléfono, y eso se calcula al descargar (HU-SYNC-011).

- **Quién ve qué.** El colportor ve las ubicaciones de su ciudad de trabajo (`mis_ciudades_de_trabajo()`: la de su zona asignada; sin zona, todas las de la campaña, S55) y las que registró él. Cuentan las campañas en las que tiene una inscripción viva y que no terminaron: en curso o por empezar, igual que el mapa (`0013`, decisión del 02/10: las casas de una campaña futura se bajan antes del primer día); registra en cualquier lado (R-CM04). El coordinador y el ADMIN las ven todas. `espacio` y `house_status` siguen a su ubicación, y también los ve quien los cargó.
- **Quién escribe dónde.** La zona acota solo la lectura (decisión de Cristian del 30/09, #36): el colportor corrige ubicaciones y carga espacios y estados en todas las ciudades de sus campañas ya empezadas y no terminadas, o terminadas hace 15 días o menos (`0020`), tenga zona o no (`mis_ciudades_de_campania()`, `puedo_escribir_en_ubicacion()`). Lo que cargó sin señal en una casa de otra ciudad de su campaña sube aunque después le asignen una zona en otra ciudad: el espacio, y colgando de él la persona, la visita y la venta. Lo que sigue sin subir es la corrección de una fila que la lectura ya no le deja ver y que no es de la gracia (el push la lee antes: `FILA_INEXISTENTE`, sin borrar nada del teléfono); en la gracia, `CG001` (más abajo).
- **Corregir lo que cargó, solo con campaña vigente** (`0018` y `0021`, decisiones del 02/10). Un espacio o un estado se corrige o se da de baja mientras el colportor tiene alguna campaña en la que escribir: vigente, o terminada hace 15 días o menos (`0020`), aunque sea de otra ciudad. Vale también para la casa que registró él: sin ninguna, no la corrige, no la muda ni la da de baja. El push vuelve `invalid` 42501, visible en la cola de error, y no se pierde nada. **Las altas no miran la campaña**: el depto y el estado de una casa nueva propia entran aunque la campaña no haya empezado (las casas también se cargan antes del primer día, igual que el mapa); en una casa ajena el alta sigue pidiendo campaña en la que escribir (`0021`, `puedo_cargar_en_ubicacion()`).
- **Corregir lo que ve, aunque todavía no pueda escribir** (`0021`). Antes del primer día de la campaña ve las casas, espacios y estados ajenos pero no los puede corregir: el push vuelve `invalid` 42501 (visible en la cola de error), no un `conflict` con `server_row` que el teléfono aplicaba pisando su corrección. Lo que no ve sigue con `FILA_INEXISTENTE`. Un UPDATE que **mueve** la fila (`ubicacion.ciudad_id`, `espacio.ubicacion_id`, `house_status.ubicacion_id`) exige poder escribir donde estaba: si no, 42501 (trigger `tg_control_de_correccion`, también por UPDATE directo).
- **Lo que sube tarde** (`0020`, decisión del 02/10). Lo que depende de la campaña (corregir una casa ajena, cargar o corregir espacios y estados) se acepta hasta 15 días después de que terminó, contados en la hora de Montevideo: el día 15 entra hasta las 23:59 y el 16 ya no. Desde `0024` el día es el mismo en todo el sistema: la lectura, la inscripción y el estado de la cuenta también lo cuentan en Montevideo, así que la campaña que termina el día D sigue vigente hasta las 23:59 de D, la lectura incluida (antes cortaba a las 21:00, por el día en UTC).
- **En la gracia, lo ajeno no se corrige: `CG001`** (`0021`, decisión de Cristian del 02/10 en #52). En los 15 días entran las ventas, las visitas, las personas, las altas (casa, espacio y estado, también en una casa ajena) y las correcciones de filas propias (las que cargó él). La corrección o baja de una casa, un espacio o un estado que cargó otro, subida después del fin de la campaña y sin ninguna campaña en curso que cubra la ciudad, vuelve `invalid` con `code: CG001`, distinto de `42501` para que el teléfono lo avise («La campaña ya terminó: solo se guardan tus ventas y lo que cargaste vos. Descartá este cambio.»). El push lo decide antes de leer la fila (la lectura no tiene gracia: sin eso volvía `FILA_INEXISTENTE`); un UPDATE directo sobre algo que ve lo rechaza el mismo código por trigger. Con otra campaña en curso en la ciudad, la corrección entra. Pasado el día 15, lo ajeno que ya no ve (lo de una casa que no es suya) sigue `FILA_INEXISTENTE`; lo ajeno que todavía ve (un depto o un estado de una casa suya) y lo propio en una casa ajena vuelven `invalid` 42501, porque no queda ninguna campaña en la que escribir.
- **Dar de baja una casa** (`0018`, decisión del 02/10). No se puede si tiene alguna venta (`UB001`) o alguna visita registrada por otro colportor (`UB002`), contando también las dadas de baja. El push lo devuelve `invalid` con ese código, sin tumbar el lote, y la casa queda como estaba; la app lo traduce a un aviso y lo revisa antes de ofrecer «Dar de baja».
- **Marcar como duplicado** (`0026`, backend-supabase#56; decisión de Cristian del 02/10, HU-UBI-006). `select public.marcar_como_duplicado(duplicada_id, conservada_id);` pasa todo lo que cuelga de B a A y da de baja B, en **una sola transacción** y de forma **idempotente**. Responde un `jsonb` con `duplicada_id`, `conservada_id`, `ya_unida`, `espacios_pasados`, `espacios_unidos`, `personas`, `visitas`, `ventas` y `cobranzas` (y, desde `0035`, `destino_id`, `tipo_conservada` y `paso_a_edificio`). Lo llama quien escribe en las dos casas (`puedo_escribir_en_ubicacion()`); si no, `42501` (también si alguna no existe). A los espacios de B los pasa a A tal cual (`espacio.ubicacion_id`, así viajan sus vínculos, visitas, agendas, ventas y cobranzas, también las de otros colportores) y **sin mezclarlos** con los de A; solo el **espacio único** (`numero_depto` nulo, de una casa o un negocio) se funde en el de A: la persona que está en los dos queda una vez, con lo de B colgando del vínculo de A (si el de A estaba dado de baja y el de B vivo, se reactiva), la que solo está en B se muda, y el único de B queda dado de baja. La fila de `house_status` de B se da de baja con B; la de A no se toca: la recalcula la app (ADR-003). La baja de B **no se bloquea** por `UB001` ni `UB002`: ya no cuelga nada de ella. `UB003` si A ya está dada de baja («La ubicación que ibas a conservar ya está dada de baja. Revisá el par de nuevo.»), `UB004` si A y B son la misma, `22023` si falta alguna. Con B ya unida, responde `ya_unida: true` sin tocar nada. Lo que un teléfono sube tarde nombrando a B ya no espera a que se vuelva a llamar: desde `0035` el servidor lo redirige a A en el momento (bullet siguiente). Las reglas de corrección de `0021` valen: con la campaña terminada hace 15 días o menos y sin otra en curso, lo que cargó otro no se corrige (`CG001`, nada queda a medias); sin ninguna campaña en la que escribir, `42501`. **No está**: qué ve el otro colportor en su teléfono y el camino sin conexión (pendientes de Cristian; la unión como trabajo del motor es backend-supabase#70).
- **La unión se recuerda, se redirige y la casa pasa a edificio** (`0035`, backend-supabase#69; decisiones de Cristian del 06/10 sobre la vista 10). `marcar_como_duplicado()` (misma firma) guarda que B se unió a A en `ubicacion_union` (`duplicada_id` único → `conservada_id`) y qué espacios únicos se fundieron en `espacio_union` (espacio de B → único de A): solo en la nube, sin columnas nuevas en las tablas que se sincronizan y sin tocar `sync.entidad` ni el contrato; las lee solo el ADMIN y las escriben únicamente las funciones de la unión. En la misma operación reapunta a A lo que nombraba a B: `espacio_persona.ubicacion_cobranza_alt_id` y `agenda.ubicacion_alt_id` (de todos los colportores) y las decisiones de `ubicacion_par_decidido` (se reordena el par para que `a < b`; la del par (A, B) mismo queda dada de baja con sus ids; si el mismo colportor ya había decidido el par nuevo, gana «conservar ambos» sobre «ignorar» y, entre dos iguales, la de `decidido_en` más reciente; la otra queda de baja). **Lo que llega después** (push, RPC o PostgREST) nombrando a B, a su espacio único ya fundido o a un vínculo fundido se guarda en A, en su espacio único o en su vínculo (triggers `<tabla>_0_union_redirige`, que corren antes que los demás y toman `FOR KEY SHARE` sobre la ubicación: una escritura a mitad de la unión espera y ve el registro). Nada se rechaza ni se pierde por eso, y la RLS de quien escribe sigue valiendo sobre la fila ya redirigida, con **una excepción acotada** en las políticas de INSERT y UPDATE de `espacio`: un depto que llega nombrando a una ubicación ya unida se guarda en la que recibió si quien lo sube podía escribir en la nombrada (aunque esté de baja), aunque no escriba en la que recibió (marca de transacción `colportores.union_espacio` que solo deja el trigger, atada al id del depto y a su destino; en el UPDATE vale solo para un depto que cargó quien lo corrige, `created_by = auth.uid()`: escribir en B no deja corregir ni dar de baja los espacios ajenos de A); quien no podía escribir donde nombró sigue con `42501`, y nombrar a A directamente no cambia. Reemplaza al «barrido con reintento» de `0026`. Cruces: B ya unida a cualquiera, o A ya unida a B (sentido contrario), responde `ya_unida: true` con el `destino_id` real; si A ya se unió a C, B va a C (y se exige escribir en C). **Unir tipos**: si la que recibe es `CASA` y queda con más de un espacio vivo, pasa a `EDIFICIO` en la misma transacción (`paso_a_edificio: true`); casa con casa o casa con un negocio de un espacio se funde y sigue `CASA`; un `NEGOCIO` con varios sigue `NEGOCIO`; un depto que sube tarde a una casa ya unida también la pasa a edificio. **No está**: las uniones hechas con `0026` antes de `0035` no tienen registro (se registran la próxima vez que se llama con ese par); `house_status` no se redirige (se da de baja con B); el alta de un segundo vínculo de la misma persona con otro id en el espacio fundido, que chocaba con el unique (`23505`), se junta desde `0064` (bullet siguiente).
- **El segundo vínculo de la misma persona se junta, no se rechaza** (`0064`, backend-supabase#105; decisión de Cristian del 21/10, «Venta tarde»: «Juntar los dos»). Si lo que sube un teléfono tarde es un vínculo (`espacio_persona`) de una persona que ya tiene uno en el espacio de A (el espacio fundido de B), el trigger de `espacio_persona` **no inserta otra fila** (ni con `ON CONFLICT DO NOTHING`): guarda en `espacio_persona_union` (`duplicada_id` único, el id que subió el teléfono y que no existe como fila → `destino_id`, el vínculo que quedó) y las visitas, agendas y ventas que lo nombran (en el mismo push, en los siguientes o por PostgREST) se guardan en el vínculo de A (`redirigir_vinculo()` sigue el registro y, desde ahí, la cadena de uniones). Si el que llegó está vivo y el de A estaba dado de baja, se reactiva; la cobranza alternativa que traía se hereda solo si el de A no tenía una. Nada se rechaza ni se pierde. El registro es solo de la nube (no está en `sync.entidad`; lo lee el ADMIN; lo escribe únicamente el trigger). **La respuesta del push** trae un resultado nuevo, `{"client_op_id", "outcome": "merged", "merged_into": "<id del vínculo que queda>"}` (el motor lo cierra como `DONE` y reapunta lo local sin borrar nada: front-colportores-mobile#178; contrato §6.1): reintentar el alta, con el mismo `client_op_id` o con otro, vuelve a dar `merged` con el destino de hoy, y `sync.push` lo cuenta entre los aceptados del `sync.log`. Un alta de un id que ya existe sigue siendo `duplicate`. **No está**: el `update` o `delete` de un vínculo que se juntó (el id ya no existe) sigue dando `FILA_INEXISTENTE`; y mover un vínculo que ya existe al espacio fundido, donde su persona ya está en A, sigue como en `0035` (queda dado de baja donde llegó).
- **Qué baja** (`0023`, backend-supabase#58; decisión de Cristian del 02/10, HU-SYNC-011). El pull baja siempre **toda la ciudad de la zona del colportor**, más las ubicaciones que registró él; sin zona, todas las ciudades de su campaña. No hay elección de alcance: el parámetro `alcance` de `sync.pull` sigue en la firma para que un motor viejo no se rompa, pero el servidor lo ignora (no hay `22023`). Con cada ubicación bajan sus espacios y su estado, también las bajas (su tombstone). `sync.entidad.columna_ubicacion` marca qué entidades bajan así. La zona ya no recorta lo que baja: solo decide la ciudad.
- **Área completa, solo si aparece una ciudad** (decisión del 02/10). El watermark de `ubicacion`, `espacio` y `house_status` guarda, junto a la huella, la lista de ciudades de trabajo que tenía en ese pull (`area` y `ciudades`; para el motor son opacas, el watermark se devuelve tal cual). Si la lista de ahora tiene una ciudad que la guardada no tenía (lo inscriben en otra campaña, le asignan una zona de otra ciudad, una campaña que terminó vuelve a estar vigente), la entidad baja completa, también lo que se cargó antes de su último pull, y el pull lo dice en `area_reset`. Si la lista es igual o se achica (le dan una zona de una de sus ciudades, termina una de sus campañas), no baja nada de nuevo: el delta sigue y la lista nueva se guarda; lo de la ciudad que se fue deja de actualizarse, sin borrarse. Si después vuelve a crecer, esa ciudad ya no estaba en la lista guardada: baja completa. Un watermark sin lista (de un teléfono de antes de `0023`) se compara por la huella, como antes: a lo sumo un reinicio, y el watermark que sale ya lleva la lista. Cambiarle la zona dentro de la misma ciudad, redibujarla, renombrarla o cambiarle el color no baja nada. El día que una campaña empieza tampoco: sus casas ya habían bajado. Límite conocido: el reinicio baja toda la lista de ahora, no solo la ciudad nueva.
- **Lo que sale de la ciudad** (`0016` y `0023`, backend-supabase#37). Si una casa que el colportor tenía en una de sus ciudades pasa a una que no es suya, su pull siguiente la avisa en `out_of_area`: `{"ubicacion": [ids]}`. La app la marca como fuera de su ciudad y no borra nada. Corregir la posición dentro de la misma ciudad no es salir: la casa sigue bajando como fila. Un trigger anota en `sync.ubicacion_movida` la posición y la ciudad de antes de cada cambio de posición o de ciudad (`0016`); el aviso mira solo la ciudad. Cuando aparece una ciudad en la lista, la entidad arranca de cero y el pull lo dice en `area_reset`: lo que el teléfono tenía de una ciudad que dejó de ser suya queda ahí, sin actualizarse (el servidor no manda borrados). La forma del aviso es una propuesta, pendiente del acuerdo con el motor (front-colportores-mobile#178).
- **Una casa que se mueve.** Si cambia la posición o la ciudad de una ubicación, sus espacios y su estado se republican, y le llegan a quien la empieza a tener en sus ciudades (el cambio de ciudad). Republicar sube solo `xmin_w`, no `sync_version` ni `updated_at` (la GUC local `colportores.republicar` en `tg_auditoria_update`): así no vuelve `conflict` lo que un teléfono tenga pendiente sobre esas filas. `house_status.lat`/`lon` (el pin) los pone el servidor con la posición de la casa; el push los descarta.
- **Supuestos de HU-SYNC-011 (decididos el 30/09 y el 02/10).** «La ciudad» es la de su zona asignada; sin zona, todas las de la campaña (las que no terminaron); acota lo que baja y lo que ve, no dónde escribe. Ya no hay alcance que elegir (S54 y S60 quedaron sin efecto el 02/10). Las casas de una ciudad que dejó de ser suya no se borran del teléfono: quedan sin actualizarse, y un área que se achica no baja nada de nuevo.
- **Posible duplicado** (aviso, no bloqueo). `posibles_duplicados_de_ubicacion(ciudad_id, calle, numero, lat, lon, excluir_id)` devuelve las ubicaciones visibles con la misma dirección normalizada (trim y minúsculas) o a menos de 5 m.
- **Dirección única (D1, `0017`).** Dos ubicaciones vivas de la misma ciudad con la misma calle y número normalizados (sin tildes ni espacios de más) no pueden estar a menos de 100 m: `23505` con la restricción `ubicacion_direccion_unica`. En el push vuelve `conflict` sin `server_row`: la fila queda en el teléfono y se resuelve en la vista 10. Lo que cuelga de esa alta en el mismo lote (el depto, la persona, la visita, la venta, el estado) vuelve `conflict` con `code: ESPERA_ALTA_EN_CONFLICTO` y `depends_on` (decisión del 02/10): no se escribe y el motor lo reintenta cuando se resuelve el alta. La migración no da de baja nada: si la base tiene direcciones repetidas a menos de 100 m, aborta y las lista todas (decisión del 02/10).
- **La unión baja al teléfono y no se reactiva** (`0051`, backend-supabase#107; decisión de Cristian del 21/10, «Marca unión»; cambia la del 16/10 de que la unión quedara solo en la nube). El pull de `ubicacion` (y el `server_row` de un conflicto) trae en cada fila la clave `unida_a_id`: el id de la ubicación a la que se unió (`ubicacion_union.conservada_id`, `public.ubicacion_unida_a(uuid)`) o `null`. No es una columna: sale de `sync.expresion_json`, así que el teléfono no puede escribirla (un push que la mande se ignora) y `ubicacion_union` sigue siendo la única fuente y de lectura exclusiva del ADMIN. Es el destino de esa unión: si después esa se une a otra, la marca de B no cambia. Para que baje por delta, registrar una unión toca a B (sube su `sync_version` y su `xmin_w`; si la unión ya la dio de baja en la misma operación, no hace falta); la migración toca una vez a las B de las uniones ya registradas. **Reactivar una B unida** (`deleted_at` de no-null a null) se rechaza con `UB005` y el texto «Esta ubicación se unió a otra y no se puede reactivar.»: por push (`invalid`, sin tumbar el lote, `sync.aplicar_job`), por RPC o por PostgREST (un trigger que corre antes que los demás); una baja común se sigue reactivando. Móvil: la réplica guarda `unida_a_id` y la leyenda y la guarda de «Reactivar» salen de ahí (front-colportores-mobile#178). Docs: contrato del sync y `esquema-datos.md` (docs-organizacion#72).
- **Pares de ubicaciones ya decididos y la métrica R21** (`0032`, backend-supabase#35; decisión 6 de mobile#207, HU-UBI-006). `ubicacion_par_decidido` guarda lo que cada colportor eligió ante un posible duplicado: el par ordenado (`ubicacion_a_id` < `ubicacion_b_id`), `decision` (`CONSERVAR_AMBOS` o `IGNORAR`) y `decidido_en`. Sube por push, sin alsoPull; baja por pull solo para quien la tomó (`columna_duenio = created_by`, también al reinstalar). La RLS deja a cada colportor lo suyo y ni el coordinador ni el ADMIN la leen directo. Una sola decisión viva por colportor y par; una baja es `deleted_at`, no se borra. `select * from public.metrica_r21();` devuelve una fila con `decisiones`, `conservar_ambos`, `ignorar` y `proporcion_conservar_ambos` (null sin decisiones) de todos los colportores, solo números; solo el ADMIN (`42501` para otro rol o sin sesión). Cuando una de sus ubicaciones se une a otra, el par se reapunta solo (`0035`, backend-supabase#69). **No está**: la columna `motivo` (ni el teléfono ni `esquema-datos.md` la tienen).

### Acompañamientos del coordinador (sin BFF)

Desde la migración `0043` (backend-supabase#97, HU-JOR-004, vista 33 «Equipo», decisión de Cristian del 21/10 «C13», [docs#69](https://github.com/Colportores/docs-organizacion/issues/69)) el coordinador completa el dato «acompañé al colportor X el día Y» cuando el colportor se olvidó de marcarlo, y ve por colportor el historial de acompañamientos y los días sin acompañar. Cuatro RPC que el panel llama directo ([ADR-013](https://github.com/Colportores/docs-organizacion/blob/main/docs/decisiones/ADR-013-clientes-directo-a-rpc-de-supabase.md)); no hay tablas ni columnas nuevas: todo sale de `jornada.acompaniante_id`.

```sql
select * from public.acompaniamientos_por_colportor(campania_id);                -- la tabla: total, último y días sin acompañar
select * from public.historial_de_acompaniamientos(campania_id, colportor_id);   -- «Ver historial» (sin colportor: el de todos)
select * from public.jornadas_cerradas_de_colportor(campania_id, colportor_id);  -- las jornadas entre las que elegir (acompaniante null = libre)
select * from public.agregar_acompaniamiento(campania_id, jornada_id);           -- «Registrar acompañamiento»
```

- **Qué cuenta.** Una jornada viva con acompañante de un colportor inscripto en la campaña, que empezó entre su `fecha_inicio` y su `fecha_fin` (día de `America/Montevideo`, ambos incluidos). Una inscripción dada de baja sigue contando lo anterior a la baja en el historial (no en la tabla, que lista las inscripciones vivas). Las jornadas **abiertas** con acompañante cuentan (`horas` es `null`, `en_curso` es `true`). Acompaña cualquiera (de cualquier coordinador).
- **Días sin acompañar.** Días corridos desde el último acompañamiento; si nunca lo hubo, desde el **inicio de la campaña** (`ultimo_dia` es `null` y `contado_desde` dice desde qué día se contó: el panel escribe «Nunca» y «N días desde el inicio»). Sin umbral. Una campaña por empezar da 0. La tabla sale con más días sin acompañar primero. La HU dice «desde que se inscribió»; gana el canvas y el issue (inicio de la campaña).
- **Agregar.** `jornada.acompaniante_id` = quien llama (el coordinador de la campaña o un ADMIN). Solo una jornada **cerrada** de un colportor de esa campaña. Es idempotente: si ya es suyo, `ya_estaba` es `true` y la fila no se toca (un doble toque no sube la versión). Errores: `JO001` la jornada no existe, está dada de baja o no es de un colportor de esa campaña (los tres contestan igual); `JO002` sigue abierta; `JO003` ya la acompañó otra persona (nunca se pisa); `JO004` es del propio coordinador; `CZ011` la campaña ya terminó (las lecturas sí se hacen); `22023` sin jornada. El UPDATE sube `sync_version`: si el teléfono todavía tiene un push de esa jornada, vuelve `conflict` y gana el servidor.
- **Qué no devuelven.** Ni clientes, ni visitas, ventas, importes o ubicaciones, ni el email, ni la hora de inicio y fin: el día, las horas de la jornada y el nombre de quien acompañó.
- **Quién.** Con el JWT del coordinador de la campaña (o un ADMIN): sin sesión, colportor, sin rol, rol vencido o coordinador de otra campaña, `42501`, antes de mirar nada; campaña inexistente o dada de baja, `CZ001`. `SECURITY DEFINER` con `search_path` vacío (el coordinador no lee `jornada`), `VOLATILE` (`supabase-js` las manda por `POST`), `EXECUTE` solo para `authenticated`.
- **Pendiente de decisión.** Elegir a **otro colportor** como acompañante, la **nota** opcional y «de dónde salió el dato» (el canvas los muestra; la HU dice «no hay datos nuevos»), y el `audit_log` que nombra la HU (la tabla no existe): ver el PR.

### Zonas de cada colportor para Equipo (sin BFF)

Desde la migración `0047` (backend-supabase#98, HU-CAM-006, vista 33 «Equipo», [docs#69](https://github.com/Colportores/docs-organizacion/issues/69)) el panel lee de una sola vez la zona de hoy de cada colportor y sus **zonas anteriores con fechas**, que salen del historial de la `0022` (`campania_colportor_zona_historial`, que hasta ahora ninguna lectura devolvía).

```sql
select * from public.zonas_por_colportor(campania_id);
-- colportor_id, nombre, apellido, ciudad_id, ciudad_nombre, zona_id, zona_nombre, zona_desde, zona_desde_inicial, zonas_anteriores, casas_registradas
```

- **Una fila por inscripto vivo** de la campaña (los mismos de `colportores_de_campania()`: inscripción viva y cuenta no dada de baja), con o sin zona, por apellido y nombre. `zona_id`, `zona_nombre`, `ciudad_*` y `zona_desde` son los de hoy (todo `null` = «Sin zona»; una zona dada de baja cuenta como sin zona). La ciudad es la de la zona de hoy, como en `acompaniamientos_por_colportor()`.
- **`zonas_anteriores`** es un `jsonb`: `[{zona_id, nombre, ciudad_id, ciudad_nombre, desde, hasta, inicial, eliminada}]`, uno por tramo ya cerrado, del más viejo al más nuevo; `[]` si nunca tuvo otra. Las fechas son el **día de Montevideo** del cambio (un tramo cierra el mismo día en que abre el siguiente). La misma zona puede figurar más de una vez, y `ciudad_nombre` distingue dos zonas con el mismo nombre. `eliminada` marca una zona dada de baja después; sigue figurando con el nombre que tenía.
- **`inicial` / `zona_desde_inicial`**: el tramo ya existía cuando se activó el historial (`0022`) y su `desde` es una cota, no la fecha real de la asignación. El panel decide cómo mostrarlo.
- **Quién.** Igual que `acompaniamientos_por_colportor()`: el coordinador de la campaña o un ADMIN, `42501` antes de mirar nada, `CZ001` si la campaña no existe, y una campaña **por empezar o terminada se lee** (el historial se consulta también al cierre). Sin email ni clientes. `SECURITY DEFINER`, `VOLATILE`, `EXECUTE` solo para `authenticated`.
- **`casas_registradas`** (0062; decisión del orquestador, 21/10, gana el canvas): un número, las ubicaciones **vivas** que creó el colportor (`created_by`) en las ciudades **vivas** de la campaña, **desde que se inscribió** (`campania_colportor.created_at`, el mismo inicio que los acompañamientos) **y hasta el último día de la campaña** (`fecha_fin`, día de Montevideo, inclusivo; sin fecha de fin, sin tope; lo cargado en los días de gracia después del cierre no cuenta, como en los acompañamientos). Si dos inscripciones vivas del colportor tienen campañas superpuestas en la misma ciudad, las mismas casas figuran en las dos (queda atado a la decisión pendiente de «campañas superpuestas» de la 0043). No mira la zona: las casas de una zona anterior siguen contando, y cambiar de zona o quedar sin zona no resta nada. No cuentan las dadas de baja, las anteriores a la inscripción, las posteriores al cierre de la campaña ni las de una ciudad que no es de la campaña.

### Tablero de Inicio del panel (sin BFF)

Desde la migración `0054` (backend-supabase#94, HU-CAM-008, vista 31 «Inicio», [docs#69](https://github.com/Colportores/docs-organizacion/issues/69)) el panel lee el día de la campaña con una sola llamada: las cifras de cada ciudad y, dentro, las de cada colportor.

```sql
select public.tablero_de_inicio(campania_id);              -- hoy (día de Montevideo)
select public.tablero_de_inicio(campania_id, '2026-10-21'); -- un día anterior (uno futuro es 22023)
-- jsonb: fecha, es_hoy, calculado_a, total, ciudades[ {ciudad_id, nombre, cantidad_colportores, en_jornada, horas,
--        presentaciones, ventas, monto_total, colportores[ {colportor_id, nombre, apellido, estado, horas,
--        presentaciones, ventas, monto_total, ultimo_push_at} ]} ], sin_zona[], pendientes[]
```

- **Cifras del día.** `estado` es `EN_JORNADA` (jornada abierta que empezó hoy), `SIN_CERRAR` (un día anterior: la jornada de ese día quedó abierta; el panel dice «Sin cerrar»), `FINALIZADA` o `SIN_INICIAR` y sale solo de la jornada; `horas` suma las jornadas que empezaron ese día (la abierta de hoy cuenta hasta ahora; la abierta de un día anterior no inventa un fin: solo suman las cerradas); `presentaciones` son las visitas `VENTA` o `ENTREVISTA` (HU-VIS-005, C1; `RECHAZO` provisorio no, S62); `ventas` y `monto_total` (en **centavos**) son las del día. `ultimo_push_at` es el de `usuario` (0053), solo para mostrar «hace X».
- **Ciudad.** La de la zona actual del colportor (mismo criterio que `horas_por_ciudad_y_colportor` y `ventas_por_ciudad_y_colportor`). `ciudades` trae todas las ciudades vivas de la campaña, también las que no tienen colportores; el departamento todavía no (se suma cuando llegue backend-supabase#92: por ahora el panel lo toma de `ciudades_de_campania()`).
- **Sin zona.** Un colportor sin zona (o con la zona o la ciudad de la zona dadas de baja) no entra en ninguna cifra: va aparte en `sin_zona` (de ahí sale «Colportora sin zona asignada»). Los inscriptos son los vigentes ese día, como en los reportes (inscripción creada antes de que termine el día y sin baja, o con la baja posterior al comienzo del día): quien no estaba inscripto no figura, y quien se dio de baja después va en `sin_zona` con `inscripcion_de_baja: true` (solo cuentan sus jornadas anteriores a la baja, para su estado). Cada uno de `sin_zona` trae `inscripto_at` (cuándo se inscribió: «se sumó hoy a las 11:02»).
- **Pendientes.** `pendientes` es `[]` hasta que V2 conecte los tickets por validar y los pedidos por autorizar.
- **Quién.** Con el JWT del coordinador de la campaña (o un ADMIN): sin sesión, colportor, sin rol, rol vencido o coordinador de otra campaña, `42501`, antes de mirar nada; `CZ001` si la campaña no existe; una campaña terminada se lee. Solo cifras: ni clientes, ni ubicaciones, ni talonarios, ni emails.

## Stock y cuenta (V2): el esquema, sin reglas todavía

Desde la migración `0067` (backend-supabase#100, [docs#69](https://github.com/Colportores/docs-organizacion/issues/69), decisiones del 21/10) están las tablas y columnas de la V2; se conectan después del 20/11 (plan-sprints §5). **Es solo esquema**: ninguna regla de negocio corre todavía (ni la deuda al autorizar un pedido, ni el stock al recibirlo, ni acreditar al validar un ticket).

- **Columnas nuevas, opcionales.** `campania.alquiler_monto` (centavos; `null` = no cobra alquiler), y en `campania_colportor`: `tipo_beca` (`null` / `MEDIA` / `COMPLETA`), `meta_monto_ces` y `limite_pedido` (centavos; `null` = sin límite). Bajan al teléfono con la inscripción y la campaña. La beca, la meta y el límite solo los cambian el ADMIN o el coordinador **de esa campaña** (`42501` para otro coordinador o el propio colportor); el servidor, sin restricción. Se cargan a mano con un `update` mientras no exista la pantalla de Equipo.
- **Tablas nuevas, vacías:** `stock`, `pedido_casa_editora` (con `origen` y `excede_limite`) y `pedido_item`, `movimiento_stock`, `transferencia_stock` y `transferencia_item`, `deposito` (con `destino` y `concepto`), `ticket` y `estado_cuenta` (con `deuda_alquiler`). Estados del pedido: `BORRADOR`, `PENDIENTE_AUTORIZACION`, `AUTORIZADO`, `DESPACHADO`, `RECIBIDO`, `RECHAZADO`, `CANCELADO`; de la transferencia: `PENDIENTE_AUTORIZACION`, `AUTORIZADO`, `EJECUTADO`, `RECHAZADO`, `CANCELADO`; del ticket: `PENDIENTE`, `VALIDADO`, `RECHAZADO` (rechazar exige motivo; un ticket resuelto no se edita, `TK001`, salvo la foto, que vence a los 4 meses).
- **Quién lee.** El dueño, el ADMIN y el coordinador de una campaña donde el colportor está o estuvo inscripto (`coordina_al_colportor()`); una transferencia la ven las dos puntas. **Quién escribe:** nadie con un JWT (sin políticas de INSERT/UPDATE): lo decide la conexión de V2. Ninguna tabla está en `sync.entidad` ni en Realtime hasta que el contrato de sync las incluya.
- **Ojo con el nombre.** La tabla `estado_cuenta` convive con la función `estado_cuenta()` de la `0004` (ACTIVA / PENDIENTE_ASIGNACION / SUSPENDIDA): no se pisan, pero conviene renombrar una.

## Privacidad

Los datos personales de clientes (`persona.nombre`, `persona.apellido`, `persona.telefono`, `nota.texto`) son **local-only**: viven solo en el dispositivo del colportor y nunca llegan al cloud, por la Ley 18.331 de Uruguay. Ver [`02-restricciones.md`](https://github.com/Colportores/docs-organizacion/blob/main/docs/02-restricciones.md).

**Este backend no tiene tablas `persona` ni `nota`.** No es una omisión temporal: es la restricción de diseño.
